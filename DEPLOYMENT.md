## 2. Cloud deployment — Render

`render.yaml` is a Render Blueprint describing all three services. Nothing in it
is a secret: `SECRET_KEY` and `PRIVGUARD_SERVER_SECRET` are generated by Render (the app refuses to start in production if either is a known placeholder), `DATABASE_URL` is injected from
the managed database, and the two cross-service URLs are prompted for.

### Two-pass sequence

Neither service knows the other's public URL until both exist, so the first
deploy is done in two passes.

**Pass 1 — create the services.**

1. Render dashboard → **New** → **Blueprint** → select this repository.
2. Render reads `render.yaml` and shows `privguard-db`, `privguard-api`,
   `privguard-ui`. It prompts for the two `sync: false` values — enter
   placeholders for now:
   - `CORS_ALLOWED_ORIGINS` → `https://privguard-ui.onrender.com`
   - `VITE_API_BASE` → `https://privguard-api.onrender.com/api`
3. Apply. The API's `preDeployCommand` migrates and seeds the database.

**Pass 2 — correct the URLs.**

Render appends a suffix if a name is taken, so the real hostnames may differ
from the placeholders. Once both services are live:

1. Copy the actual UI URL → set `CORS_ALLOWED_ORIGINS` on **privguard-api**.
2. Copy the actual API URL + `/api` → set `VITE_API_BASE` on **privguard-ui**.
3. Redeploy both.

`VITE_API_BASE` is read at **build** time by Vite, so changing it requires a
rebuild of the UI, not just a restart.

### Verify

```bash
curl -s https://<api-host>/api/health/          # {"status":"ok",...}
curl -s -o /dev/null -w '%{http_code}\n' https://<ui-host>/
```

Then sign in as `alice` and confirm the burn-down chart renders.

> **Free tier caveat.** Render spins free services down when idle; the first
> request after a sleep takes ~50s. Wake the API before a live demo.

### Record the live URL

Add it to `README.md` once deployed — the brief requires a submitted live URL.

## 3. Docker Hub

CI builds the images; publishing them makes the build artefacts inspectable.

```bash
docker login

# Tag both images against your Docker Hub account.
docker build -t <dockerhub-user>/privguard-api:latest ./backend
docker build -t <dockerhub-user>/privguard-ui:latest  ./frontend

docker push <dockerhub-user>/privguard-api:latest
docker push <dockerhub-user>/privguard-ui:latest
```

Tag a submission snapshot alongside `latest` so the graded state stays pinned:

```bash
docker tag <dockerhub-user>/privguard-api:latest <dockerhub-user>/privguard-api:v1.0
docker push <dockerhub-user>/privguard-api:v1.0
```

## 4. Backup and restore drill

Uses PostgreSQL's native tools, as the brief requires. Scripts live in `db/`.

### Back up

```bash
# From the host, against the compose database:
docker compose exec -T db pg_dump -Fc -U privguard safehealth > backups/safehealth.dump

# Or, with psql tools installed locally:
./db/backup.sh safehealth        # writes backups/safehealth_<date>.dump
```

`-Fc` is PostgreSQL's custom format — compressed, and restorable selectively
with `pg_restore`.

### Restore

```bash
docker compose exec -T db pg_restore --clean --if-exists --no-owner \
    -U privguard -d safehealth < backups/safehealth.dump

# Then confirm the ledger survived intact:
docker compose exec -T api python manage.py verify_budgets --strict
```

### Prove the backup is usable

A dump you have never restored is not a backup. `db/verify_restore.sh` restores
into a scratch database, runs migrations, verifies the ledger hash chain, and
drops the scratch database:

```bash
./db/verify_restore.sh backups/safehealth_2026-09-05_1420.dump
```

The ledger check matters more than the row counts. `sys_budget_ledger` is
append-only and hash-chained, so `verify_budgets --strict` recomputes every
entry hash from the genesis entry. If it passes after a restore, the privacy
accounting survived the round trip byte for byte — which is the property the
ledger exists to provide.

## 5. What is deliberately not deployed

`engine/` (the Rust query engine) and `oracle/` (the Python DP reference) are
research work tracked in `IMPLEMENTATION_PLAN.md`. They are not part of the
graded application and are not deployed. The graded build is the Django +
PostgreSQL + Django ORM application described above.
